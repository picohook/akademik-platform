## 2. 2026-10-26/27 kesintisi — ne oldu, ne öğrenildi

### Kök neden 1: `image:` satırı eski imajı gösteriyordu

`docker-compose.libedge.yml` içinde `image: ${LIBEDGE_IMAGE:-akademik-platform:libedge-r2}`
ve `pull_policy: never` vardı. `up --build` yeni imajı **build etti ama çalıştırmadı**.
`--force-recreate` çözmez: **container'ı** yeniler, **imajı** değiştirmez.
Sonuç: site 9 saat boyunca `codex/lang-entry` ucundan (`9f755d6`) servis verdi.

**Kural:** sürüm atlarken ilk kontrol `image:` satırının build ettiğin imajla aynı olması.

### Kök neden 2: yanlış teşhis (benim hatam)

İlk teşhis "deploy hiç yapılmamış" idi — **yanlıştı**. Reader özellikleri canlıdaydı,
çünkü `codex/lang-entry` onları zaten içeriyordu. `spike/app/public/` iki dalda
birebir aynıydı (`app.js` blob `77d82a7`). Sorun "hangi dal" değil, "hangi imaj"dı.

### Kök neden 3: `down` yanlış komuttu

`docker compose down` db'yi de kaldırır. Tekrar `up` yapınca db **yeni IP** alır;
eski web container'ı `getaddrinfo EAI_AGAIN db` ile kopar ve `mode:"demo"`ya düşer.
Bu bir **ağ** sorunu gibi görünür ama değildir.

**Doğru restart:**

```bash
sudo docker compose ... stop web
sudo docker rm akademik-platform-prod-web-1
sudo docker compose ... up -d --no-deps web
```

### Çürütülen yanılgı: `prod_default` ağı

Bir ara "web, `akademik-platform-prod_default` ağına elle bağlanmalı" sanıldı ve
`docker network connect` çalıştırıldı. **Gereksizdi.** `docker-compose.prod.yml`
`name: akademik-platform-prod` ile başladığı için proje ağının adı **zaten**
`akademik-platform-prod_default` ve db + web ikisi de onun içinde.

`docker-compose.libedge.yml` içine `networks:` bloğu **eklemeyin**.

## 3. Deploy — doğru komut

```bash
cd /var/www/akademik-platform
git fetch origin && git pull --ff-only origin main

sudo docker compose -f docker-compose.prod.yml -f docker-compose.libedge.yml \
  --env-file .env.production --env-file .env.r2 up -d --no-deps web
```

### Yapılan gerçek hatalar (tekrarlamayın)

| Hata | Sonuç |
| --- | --- |
| Sadece `--env-file .env.r2` | `required variable DOMAIN is missing a value: set DOMAIN` |
| `--no-deps web` yerine çıplak `up -d` | caddy de başlar, nginx'le 80/443 çakışır, db gereksiz yeniden yaratılır |
| `akademik-platform-web-1` ile `docker` komutu | Gerçek ad **`akademik-platform-prod-web-1`** (`name:` öneki). Komut sessizce boş döner |
| `down` ile restart | DB yeni IP alır → `EAI_AGAIN db` |
| `up -d` yalnız `-f prod.yml` | caddy `profiles: [proxy]` ile kapalı; caddy gerekiyorsa `--profile proxy` |

Tam akış (`build` + LABEL doğrulama + SHA env) `docs/DEPLOY.md` → "Varyant 2".

## 4. Hâlâ açık işler

### 4.1 Tenant yapısı — **DÜZELTİLDİ 2026-10-27 (önceki sürüm yanlıştı)**

> **Bu bölümün önceki hâli yanlış bir teşhis içeriyordu.** "Kullanıcılar eski
> tenant'ta, giriş yapınca boş kütüphane görür, `UPDATE users SET tenant_id`
> ile taşınmalı" diyordu. Bu iddia **doğrulanmamıştı** ve en azından iki
> kurulumda **yanlış**. Yanlış teşhis üzerine `db/migrations/017-
> move-demo-users-to-libedge.sql` yazıldı; PR #16 açıldı ve **kapatıldı**.
> 017 hiçbir ortamda çalıştırılmadı. Aşağısı ölçülmüş gerçek durumdur.

**Ölçülen durum (üç ayrı kurulum, üç ayrı DB):**

| Kurulum | Tenant ID | users | works | Not |
| --- | --- | --- | --- | --- |
| `elibrary.libedge.com` (EC2) | `5799f2a5-…` | ölçülmedi | ölçülmedi | SSH anahtarı yok, bu makineden erişilemedi |
| Windows `:+443` (prod, v127) | `11111111-…` | 2 | 2 | users/works aynı tenant |
| Windows `:8080` (dev, v118) | `11111111-…` | 2 | 11 | users/works aynı tenant |

Windows üzerindeki iki kurulumda (`db-1` ve `prod-db-1`) sorgu sonucu:

```sql
begin; set local row_security = off;   -- 'akademik' sahibi olarak
select id, slug, name from tenants;    -- tek satır: 11111111-… demo-universitesi
select tenant_id, email, role from users;
  -- librarian@example.edu.tr, reader@example.edu.tr → ikisi de 11111111-…

```

**Hiçbirinde tenant ayrılığı yok.** Kullanıcı ile katalog aynı tenant'ta,
`grants` `scope_type='all'` + `active`, `withTenant` da aynı `11111111-…`
kullanıyor. Taşınacak bir şey yok.

**Boş kütüphane iddiası:** Hiçbir kurulumda doğrulanmadı. 8080'de 11, 443'te 2
kitap görünüyor; ikisi de kullanıcıyla aynı tenant'ta. "Boş" gözlemi
tekrarlanmadı.

**`5799f2a5-…` nereden geliyor:** `/api/health` bu ID'yi döndürüyor:

```js
// spike/app/server.mjs:1903
json(res, 200, { ok: true, mode: pool ? 'db' : 'demo', tenantId: TENANT_ID });
// TENANT_ID = process.env.DEMO_TENANT_ID || '11111111-...'
```

Yani health **env değerini** yansıtır, DB'de o tenant'ın var olduğunu
**kanıtlamaz**. EC2'nin `.env`'inde `DEMO_TENANT_ID=5799f2a5-…` olabilir —
bu tenant'ın DB'de gerçekten bulunduğu ayrıca doğrulanmalı.

**`row_security = off` kiminle çalışır:** Yalnızca tablo sahibi (`akademik`) ile.
Uygulama kullanıcısı `akademik_app` ile:

```
ERROR: query would be affected by row-level security policy for table "tenants"
```

Bu yüzden düz `psql` sorguları boş döner — hata vermez. Teşhis yaparken
`psql -U akademik` kullanın.

**EC2'de doğrulama (SSH oturumunda çalıştırılacak):**

```bash
cd /var/www/akademik-platform
docker exec akademik-platform-prod-db-1 psql -U akademik -d akademik -c \
  "begin; set local row_security = off;
   select id, slug, name from tenants;
   select tenant_id, email, role from users order by email;
   select tenant_id, count(*) from works group by 1;
   commit;"
```

Beklenen: tek tenant `5799f2a5-…`, kullanıcılar ve kitaplar **aynı** tenant'ta.
Eğer kullanıcılar `11111111-…`'de çıkarsa iddia yalnızca EC2 için doğrudur ve
o zaman taşıma ayrı, gerçek ölçüme dayalı bir migration olarak yazılmalıdır.

### 4.1b Ayrı bulgular (gerçek, ama 4.1 ile ilgisiz)

Bunlar 4.1'i doğrularken çıktı; çok-tenant mimarisi için doğru, bugünkü
şikâyetle ilgisi yok. Ayrı iş olarak ele alınmalı:

1. **`withTenant` kullanıcının tenant'ını kullanmıyor** — `spike/app/server.mjs`
   içinde 39 çağrı, hepsi `set_config('app.tenant_id', TENANT_ID)` yapıyor
   (env'den). `createSession` ise `user.tenant_id` kullanıyor — doğru pattern
   kodda var, `withTenant`'a uygulanmamış. Tek tenant olduğu sürece zararsız.
2. **`grantAllows` boş grant listesinde `true` dönüyor** —
   `if (!grants.length) return true;`. Yani grant hiç yoksa **tüm katalog**
   görünür. Mevcut davranış bu; değiştirmek için önce LibEdge tenant'ına bir
   grant tanımlanmalı, yoksa kullanıcılar aniden boş görür.
