## 2. 2026-10-26/27 kesintisi — ne oldu, ne öğrenildi

### Kök neden 1: `image:` satırı eski imajı gösteriyordu

`docker-compose.libedge.yml` içinde `image: ${LIBEDGE_IMAGE:-akademik-platform:libedge-r2}`
ve `pull_policy: never` vardı. `up --build` yeni imajı **build etti ama çalıştırmadı**.
`--force-recreate` çözmez: **container'ı** yeniler, **imajı** değiştirmez.
Sonuç: site 9 saat boyunca `codex/lang-entry` ucundan (`9f755d6`) servis verdi.

**Kural:** sürüm atlarken ilk kontrol `image:` satırının build ettiğin imajla aynı olması.

### Kök neden 2: yanlış teşhis (benim hatam)

İlk teşhis "deploy hiç yapılmamış" idi — **yanlıştı**. Reader özellikleri canlıdaydı,
çünkü `codex/lang-entry` onları zaten içeriyordu. `spike/app/public/` iki dalda
birebir aynıydı (`app.js` blob `77d82a7`). Sorun "hangi dal" değil, "hangi imaj"dı.

### Kök neden 3: `down` yanlış komuttu

`docker compose down` db'yi de kaldırır. Tekrar `up` yapınca db **yeni IP** alır;
eski web container'ı `getaddrinfo EAI_AGAIN db` ile kopar ve `mode:"demo"`ya düşer.
Bu bir **ağ** sorunu gibi görünür ama değildir.

**Doğru restart:**

```bash
sudo docker compose ... stop web
sudo docker rm akademik-platform-prod-web-1
sudo docker compose ... up -d --no-deps web
```

### Çürütülen yanılgı: `prod_default` ağı

Bir ara "web, `akademik-platform-prod_default` ağına elle bağlanmalı" sanıldı ve
`docker network connect` çalıştırıldı. **Gereksizdi.** `docker-compose.prod.yml`
`name: akademik-platform-prod` ile başladığı için proje ağının adı **zaten**
`akademik-platform-prod_default` ve db + web ikisi de onun içinde.

`docker-compose.libedge.yml` içine `networks:` bloğu **eklemeyin**.

## 3. Deploy — doğru komut

```bash
cd /var/www/akademik-platform
git fetch origin && git pull --ff-only origin main

sudo docker compose -f docker-compose.prod.yml -f docker-compose.libedge.yml \
  --env-file .env.production --env-file .env.r2 up -d --no-deps web
```

### Yapılan gerçek hatalar (tekrarlamayın)

| Hata | Sonuç |
| --- | --- |
| Sadece `--env-file .env.r2` | `required variable DOMAIN is missing a value: set DOMAIN` |
| `--no-deps web` yerine çıplak `up -d` | caddy de başlar, nginx'le 80/443 çakışır, db gereksiz yeniden yaratılır |
| `akademik-platform-web-1` ile `docker` komutu | Gerçek ad **`akademik-platform-prod-web-1`** (`name:` öneki). Komut sessizce boş döner |
| `down` ile restart | DB yeni IP alır → `EAI_AGAIN db` |
| `up -d` yalnız `-f prod.yml` | caddy `profiles: [proxy]` ile kapalı; caddy gerekiyorsa `--profile proxy` |

Tam akış (`build` + LABEL doğrulama + SHA env) `docs/DEPLOY.md` → "Varyant 2".

### 4.1b Ayrı bulgular (gerçek, ama silme işiyle ilgisiz)

Çok-tenant mimarisi için doğru; bugünkü kullanıcı sorunuyla ilgisi yok. Ayrı iş:

1. **`withTenant` kullanıcının tenant'ını kullanmıyor** — `spike/app/server.mjs`
   içinde 39 çağrı, hepsi `set_config('app.tenant_id', TENANT_ID)` yapıyor
   (env'den). `createSession` ise `user.tenant_id` kullanıyor — doğru pattern
   kodda var, `withTenant`'a uygulanmamış. EC2 tek tenant'a servis verdiği
   sürece zararsız; ikinci gerçek müşteri geldiğinde kırılır.
2. **`grantAllows` boş grant listesinde `true` dönüyor** —
   `if (!grants.length) return true;`. Grant hiç eşleşmezse **tüm katalog**
   görünür. EC2'deki grant'ın `subject_id`'si Demo tenant'ını gösterdiği için
   (`tenant_id=LibEdge`, `subject_id=Demo`) hiçbir kullanıcıyla eşleşmiyor; admin
   tam da bu yüzden 13 kitabın hepsini görüyor. `subject_id` düzeltilirse
   davranış değişmez (aynı koleksiyon, aynı 13 kitap). Ama `grantAllows` `false`
   yapılırsa grant düzeltilmeden site boşalır — ikisi birlikte ele alınmalı.
